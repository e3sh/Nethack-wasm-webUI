# モバイル向け DOM UI システム仕様書

## 1. 概要
本プロジェクトのモバイル版 (`mobile.html`) では、従来の Canvas ベースの描画エンジンに代わり、HTML 要素を直接操作する **DOM レンダラー** を採用しています。これにより、モバイル端末での消費電力低減、文字の鮮明化、およびタイル表示の高速化を実現しています。

## 2. 構成コンポーネント

### 2.1 mobileCurses.js
`jncurses.js` をモバイル向けに再実装したクラスです。
- **軽量化**: Canvas のピクセル操作やフレーム毎の全画面クリアを廃止。
- **行ベースの更新**: 各行を `div` 要素（`.jn-line`）として保持。テキストが変化した行のみを更新することで、DOM 操作を最小限に抑制します。
- **ハイブリッド描画**: 
  - 通常のテキスト（日本語含む）はブラウザのネイティブレンダリングを使用。
  - 特殊なグリフ（タイル画像）は `span` 要素と CSS Background Sprite により描画。

### 2.2 domRenderer.js
DOM ベースでのメニュー表示や入力プロンプトのオーバーレイ管理を担当します。

### 2.3 mobile.html
モバイル専用のエントリポイントです。
- `ui-root` 要素内に `mobileCurses` が展開されます。
- `virtual-pad` 要素により、ゲームエンジン (`inputGridPad.js`) と同期したタッチボタンを表示します。

## 3. 主要機能の仕組み

### 3.1 日本語・マルチバイト文字の表示
Canvas 版ではビットマップフォントを合成していましたが、DOM 版では OS 標準の等幅フォントを使用します。これにより、ピンチズーム時も文字が美しく保たれます。

### 3.2 タイル（グリフ）表示
NetHack の各タイルは、`tileset` 画像からの CSS 切り出し (`background-position`) によって `span` 要素としてテキスト行の中に埋め込まれます。
- **グリフ判定**: 文字列中の `0x100` 以上のコード（JIS漢字圏を除く）を自動的にタイルとして識別します。

### 3.3 自動セーブ連携遷移
モバイル版からデスクトップ版（Canvas版）へ切り替える際、以下のシーケンスが自動実行されます。
1. `window.g.rogue.playing` フラグでプレイ状況を確認。
2. プレイ中の場合、`Shift+S` (Save) → `y` (Confirm) → `Space` (Finalize) を順次送信。
3. エンジンの終了（`playing` フラグの解除）を監視。
4. IndexedDB へのファイル同期を待機してから `index.html` へ遷移。

## 4. パフォーマンスへの配慮
- **差分更新**: `line.textContent !== nextText` のチェックにより、不必要な DOM 反映を回避。
## 5. 現在の課題と今後の展望（レスポンシブ・小画面対応）

### 5.1 背景と現状の再整理
- **目的の達成**: DOM版の導入により、処理負荷の軽量化という当初の目的は達成されています。
- **描画方式の変遷と課題**: 
    - 開発当初、Canvas版が固定解像度だったため小画面ではみ出す問題がありましたが、現在はCanvas版もウィンドウサイズ追従となったため、画面内に収まるよう改善されました。
    - 一方でDOM版は、現在Canvas版と同じ固定レイアウトを模倣しているため、高解像度タブレットでは問題ないものの、低解像度のスマートフォン端末では要素が画面外に溢れ、プレイが困難な状態にあります。

### 5.2 今後の課題：レスポンシブレイアウトへの対応
DOMレンダリングの利点（CSS等による外部制御の容易さ）を活かし、端末サイズに合わせた柔軟なレイアウト管理が求められます。

- **可変ウィンドウレイアウト**: 端末の解像度や向き（縦横）に応じて、ゲーム内ウィンドウの位置・サイズを動的に変更し、必要な情報が必ず画面内に収まるようにします。
- **最小表示モード（MINIMUM設定）の検討**:
    - **メッセージ表示**: 極端な例として3行程度に制限。
    - **ステータス表示**: HP/MPの％メーターや重量負荷など、プレイに必要最小限の情報に絞ったモードの検討（詳細は「^X」で確認可能とする）。
    - **メニュー表示**: 選択メニューウィンドウは全表示が必須となるため、行数可変がプレイに与える影響を慎重に検討する必要があります。
- **表示領域の最適化**:
    - 現在の横スクロールに加え、縦スクロールも導入し、最小表示を実現。
    - 画面の一部に「縮小マップ」を常時表示し、全体状態を把握しやすくする工夫。

### 5.3 実装上の検討事項
- **ゲーム本体への影響回避**: 現在 `ioControl` が行っているウィンドウレイアウト管理を、DOM版ではCSS/JSによる外部操作として切り出すことで、コアロジックを汚さない実装を目指します。
- **調整コストの評価**: 端末ごとのボタン配置、ウィンドウサイズ、行数などの調整項目が多岐にわたるため、WebUIの責務範囲を考慮しつつ、実用的な落とし所を検討する必要があります。
