# NetHack 翻訳システム次世代刷新・拡張設計構想 (Architecture Enhancement Plan)

## 1. 背景と課題提起 (Background & Issues)

現在の NetHack Wasm WebUI における翻訳システム（`TranslationEngine.js` および `dictionary.csv`）は、完全一致翻訳からスタートし、正規表現パターン置換や品詞指定（`:adj`, `:verb`）など多くの進化を遂げてきました。

しかし、翻訳機能が高度化するにつれて、初期の「フラットな単一辞書構造（約18,000行がほぼ単一大分類 `Message` に集約）」に起因するいくつかの構造的課題が明らかになってきました。

### 主な課題

1. **動的変形（かすれ文字）による翻訳ヒット漏れ**
   - NetHack では地面の刻み文字（Engraving）が歩行や時間経過でランダムにかすれる（例: `Elbereth` $\to$ `El?ereth`）。
   - 固定の完全一致辞書では無数の欠損パターンに対応できず、せっかく登録されている訳語が活用されない。
2. **コンテキスト（小分類・文脈）の欠如と誤訳（誤爆）リスク**
   - 短い単語や一般的なフレーズに対してファジーマッチ（類似度判定）を適用しようとすると、無関係なゲーム内メッセージに誤ってマッチ（誤訳）してしまう。
   - アイテム名、戦闘ログ、噂話（Rumors）、地面の落書き（Engraving）などが同一の名前空間に混在しているため、検索スコープを安全に絞り込めない。
3. **C本体（Wasm）のかすれ処理によるマルチバイト（日本語）破壊**
   - NetHack C 本体の `wipeout_text()`（`src/engrave.c`）は1バイト（ASCII）単位で文字を削る/置換するため、プレイヤーが入力した UTF-8 日本語（3バイト）の途中バイトが破壊されて文字化け（``）を起こす。

## 2. 刷新アイデアと基本方針 (Design Principles)

既存の辞書資産（約18,000行）を無駄にせず、段階的にシステムを高度化するための基本方針です。

1. **完全下位互換の維持（ゼロからの作り直しを回避）**
   - 既存の辞書データやフォーマットを破壊せず、未分類の項目はデフォルトの「一般メッセージ」としてそのまま動作させる。
2. **Cソース資産を活用した自動分類（マイグレーション）**
   - 1行ずつの手動分類ではなく、NetHack 本体の元データ（`dat/engrave.txt`, `dat/rumors.tru`, `src/*.c` 等）と照合するスクリプトによって、既存の英文に対して `Engraving`, `Rumor`, `Combat` などの小分類タグを一括自動付与する。
3. **コンテキスト限定ファジーマッチング（安全なあいまい検索）**
   - あいまい検索（レーベンシュタイン距離等）の探索対象を「落書き（`Engraving`）カテゴリのみ」かつ「文字数や類似度（85%以上など）の閾値条件」に限定することで、誤訳リスクを極小化しつつかすれたメッセージを復元する。

## 3. 辞書データ構造の拡張案 (Dictionary Schema Extension)

`dictionary.csv` または次世代辞書形式に、以下のようなメタデータ列・属性を導入します。

| 項目名 (Header) | 型 / 例 | 説明 |
| :--- | :--- | :--- |
| **Group** | `Message` / `Entity` / `Item` / `Pattern` | 従来の大分類（下位互換） |
| **Category** (新設) | `Engraving`, `Rumor`, `Combat`, `ItemName`, `System`, `Dialog` | 文脈・用途の小分類 |
| **Strategy** (新設) | `exact` (デフォルト), `fuzzy`, `regex` | 許容するマッチングルール |
| **FuzzyOptions** (新設) | `min_len:8,max_dist:2,ratio:0.85` | ファジーマッチ適用時の閾値設定 |
| **Source** | 英語原文 / パターン | 原文 |
| **Translation** | 日本語訳 | 訳文 |

## 4. 多段翻訳パイプライン（Architecture Pipeline）

翻訳エンジンを段階別（パイプライン）で実行することで、高速性と安全性を両立します。

```mermaid
flowchart TD
    Input[受信メッセージ] --> Step1{1. 完全一致 (Exact Match)}
    Step1 -- ヒット --> Output[日本語訳を出力]
    Step1 -- ミス --> Step2{2. 正規表現枠組み (Pattern Match)}
    
    Step2 -- ヒット --> Extract[枠組みを日本語化 & 変数部を抽出]
    Extract --> Step3{3. 抽出テキストのコンテキスト特定}
    
    Step3 -- 'Engraving' 等の対象 --> Fuzzy{4. カテゴリ限定ファジーマッチ}
    Fuzzy -- 類似度クリア (>=85%) --> Recover[かすれ復元訳を埋め込んで出力]
    Fuzzy -- 閾値未満 --> Fallback1[抽出テキストのまま埋め込んで出力]
    
    Step3 -- 対象外 --> Fallback1
    Step2 -- ミス --> Step5[英語のまま出力 / 未翻訳ログ記録]
```

## 5. WebUIcore 完結型マルチバイトエンコード設計（フロントエンド・シム方式）

C 側（Wasm）のソース改修や再コンパイルを行わずに、各モダン UI クライアント共通の基盤である **`WebUIcore`（`src/core/`）の入出力レイヤー** でマルチバイト刻みのエンコード・デコードを一括管理する方式です。

これにより、Vue, React, Svelte, Solid, Pure JS などの各クライアント側で個別対応することなく、全 UI で共通してマルチバイト入力・表示が可能になります。

### 1. エンコード送信とデコード受信フロー (`WebUIcore`)
- **入力時（WebUIcore $\to$ Wasm）**: プレイヤーが日本語を含む文字列（Engrave 等）を入力した場合、ASCII の固定長フォーマット（例: 1文字＝6文字固定 `[uXXXX]`）に変換して Wasm ドライバへ送信。
  - 例: `「たすけて」` $\to$ `[u305F][u3059][u3051][u3066]`
  - ※ 英数字のみ（例: `Elbereth`）の場合はエンコードせずそのまま通し、ゲーム本来の魔除け効果を維持。
- **受信時（Wasm $\to$ WebUIcore `TranslationEngine`）**: ゲーム内メッセージ受信時、`[uXXXX]` パターンを検知して日本語へデコードして各 UI クライアントへ配信。

### 2. 固定長フォーマットによる破損検知と耐かすれ復元
NetHack C 本体によって途中の文字が削られた（`wipeout`）場合でも、固定長（6文字ブロック）であるため**何文字目が破損したかを正確に特定**できます。

```text
正常時:     [u305F][u3059][u3051][u3066]   ➔ 「たすけて」
かすれ発生: [u305F]?u3059][u3051][u3066]   （2文字目の '[' が '?' に削られた）
            [u305F][u30?9][u3051][u3066]   （2文字目の '5' が '?' に削られた）
            
復元後:     「た?けて」 （文字位置・文字数を完全に保って綺麗に復元）
```

- **メリット**:
  - **全UI共通化**: `WebUIcore` に集約されるため、各クライアント（Vue/React等）の個別実装が不要。
  - **Wasm非依存**: Wasm 本体の修正・再ビルドが一切不要。
  - **セーブ・表示の安全性**: NetHack 内部では純粋な ASCII として扱われるため、セーブデータ破損や文字化け（不正なバイト列）を確実に防止。
  - **かすれ耐性**: かすれ処理が発生しても、日本語の文字数や前後関係を崩さずに「かすれ文字」として表示可能。

## 6. 段階的ロードマップ (Implementation Roadmap)

- **Phase 1: 自動タグ付けスクリプトの整備**
  - NetHack 本体の `dat/engrave.txt` や `dat/rumors.*` から英文リストを抽出し、既存の `dictionary.csv` に `Category` 列を付与するマイグレーションスクリプトを作成。
- **Phase 2: `TranslationEngine.js` のコンテキスト別ファジーマッチ実装**
  - `You read: "..."` などのパターンで抽出された落書き文字列に対して、`Category == 'Engraving'` のリスト内限定でレーベンシュタイン距離による復元処理を追加。
- **Phase 3: WebUI 側での固定長エンコード（`[uXXXX]`）シム導入**
  - 刻み入力時・メッセージ受信時に WebUI 側で固定長 Unicode タグの相互変換を行い、Wasm 本体を変更することなく日本語の文字化け防止と耐かすれ復元を実現。
