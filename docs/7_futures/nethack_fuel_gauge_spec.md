# 🧠 GKL タイムライン予測エンジン：神のご機嫌管理＆燃料計統合仕様書

本ドキュメントは、NetHack WASM WebUI におけるゲーム知識層（GKL）の拡張構想であり、プレイヤーの不可避な餓死や詰みを先読みしてダッシュボードに可視化する**「タイムライン予測エンジン（雑な燃費計＆燃料計）」**、およびその中核となる**「神のご機嫌管理システム（PrayerStatusTracker）」**の詳細設計仕様書です。

- **ステータス**: 💡 proposed (2026-09-25 策定)
- **対象ドメイン**: `src/core/knowledge/` (GKL内部ロジック), `MinimapHudRenderer.js` (ミニマップ周辺UI)
- **最上位制約**: C言語コアのメモリや内部変数（`u.ublesscnt` 等）を直接ハックせず、`SignalDetector` およびメッセージログから非侵襲的（シグナル駆動）に状態を逆算・エミュレートする。

---

## 1. 背景と目的：なぜ「お祈り」を管理するのか？

NetHackにおける「食料寿命（燃料）」を正確に予測するためには、インベントリ内の食料アイテムの総満腹度だけでなく、プレイヤーの最終セーフティラインである**「神へのお祈り（#pray）による空腹解消効果（満腹度+900相当）」**を計算に含める必要があります。

しかし、お祈りには「内部クールダウン（約300〜1000ターン）」や「神の怒り（不機嫌度）」が存在し、安全圏外でお祈りを行うと、天罰による能力低下や即死ハザードを引き起こします。

本システムでは、プレイヤーの自発的な `#pray` コマンド発行およびプロンプト応答を最初のトリガーとし、直後にCコアから返ってくるメッセージログをパースすることで、**「神のご機嫌ステータス」を決定論的にエミュレート・追跡**します。これにより、燃料計（航続可能歩数）の予備タンクに「お祈り分の+900歩」を安全に加算できるかを先読みします。

---

## 2. 状態管理（ステータス）の定義

`PrayerStatusTracker` は、以下の3つの抽象化されたステータスを保持・管理します。

| ステータス | 画面表示 | 定義・仕様 | 燃料計（予備タンク）への影響 |
| :--- | :--- | :--- | :--- |
| `🟢 SAFE` | お祈り可能 | 神の怒りがなく、クールダウンも終了している安全な状態。 | **予備燃料に「+900歩分（※）」を自動合算。** |
| `🟡 COOLDOWN` | クールダウン中 | お祈り自体は成功したが、まだ次の安全お祈りまでの猶予期間中。 | 予備燃料からお祈り分を**完全除外**。 |
| `❌ DISPLEASED` | 激怒・不機嫌 | 不敬行為やお祈りの連打により、神が怒っている致命的な状態。 | 予備燃料から**完全除外**（警告ランプ点滅）。 |

*(※) 実際の加算歩数は、その時点のプレイヤーの燃費消費効率（`burn_rate`）によって「900 / burn_rate」として雑に逆算されます。*

## 3. メッセージログからのシグナル駆動エミュレーション

### 3.1 最初のトリガー：お祈りコマンドの発行検知
1. `SignalDetector` が、プレイヤーの入力バッファまたはCコアからの「お祈り確認プロンプト（例：`Are you sure you want to pray? [yn]`）」に対する `y` の応答を検知する。
2. 内部の仮想タイマー `approximateCooldown` を「ロック（仮の最大値：1000）」状態にし、次ターンに発生するメッセージの監視を開始する。

### 3.2 直後ログによる状態確定（メッセージカタログ仕様）
お祈り実行直後のターンにCコアが出力するテキストストリームを `MessageContextResolver`（Stage 5構想に準拠）で同定します。

#### ① `COOLDOWN` への移行（お祈り成功）
以下のメッセージ群を検知した場合、神は願いを聞き届け、同時にクールダウンが開始されたとみなします。
- `"You are no longer hungry."`（空腹解消）
- `"You feel much better."`（HP回復 / 毒や病気の治癒）
- `"You feel visual stimuli."`（失明の回復）
- **処理**: ステータスを `COOLDOWN` に設定し、`approximateCooldown = 1000` とする。

#### ② `DISPLEASED` への移行（神の不機嫌・激怒）
以下のメッセージ群を検知した場合、神の怒りを買ったとみなし、通常の自然回復ルートから除外します。
- `"You feel that [神の名前] is displeased."`（不機嫌）
- `"A voice thunders: "...""`（神の怒りの声）
- **処理**: ステータスを `DISPLEASED` に設定する（自然経過でのカウントダウンは停止。祭壇での捧げ物のみで解除可能）。

#### ③ `SAFE` への即時復帰（祭壇での和解シグナル）
お祈りによる経過以外に、プレイヤーが祭壇（`_`）で死体を捧げた（`#offer`）際のログから、ご機嫌の回復をダイレクトに検知します。
- `"You have a feeling of reconciliation."`（和解したような気分がした） ➔ **`SAFE` へ復帰、タイマーを `0` にリセット。**
- `"You have a hopeful feeling."`（希望に満ちた気分がした） ➔ 神の怒りは解けたが、まだクールダウン中のため `COOLDOWN` 状態を維持（タイマーは継続）。

### 3.3 ターン経過による自動カウントダウン
`COOLDOWN` 状態の時、プレイヤーがゲーム内で1ターン行動する（`poskey` 等のターン完了イベントを購読する）ごとに、`approximateCooldown` を `-1` します。
- カウンターが `0` に達した瞬間、自動的にステータスを `🟢 SAFE` へ昇格させます。

## 4. UI/UX 統合：ミニマップダッシュボードへの配置

プレイヤーが未来の進路（次の部屋へ進むか、現在の階層に留まって食料を識別するか）を決定する瞬間に最も凝視する**「ミニマップ（`MinimapHudRenderer.js` 周辺）」**に、燃料計ランプ（LEDドット）を統合します。

```text
┌─ [🗺 Mini Map] ─────── [⛽ 🔴] ─┐  <-- ミニマップの枠上・タイトルバー等に配置
│                                │
│    . . . # . . . .             │
│    . . @ . . . . .             │
│    . . . . . . . .             │
└────────────────────────────────┘
```

### 4.1 ランプの3段階カラー仕様
- **🟢 [ECO]**: 通常消費かつお祈り・手持ちリソースともに余裕がある状態。
- **🟡 [DRIVE]**: 重量超過や指輪装備による燃費悪化、またはお祈りクールダウン中で予備タンクが細っている状態。
- **🔴 [SPORT / CRITICAL]**: お祈りも食料も尽き、数十ターン以内の「不可避の餓死（デッドロック）」が確定、または極めて近い状態。点滅アニメーションでプレイヤーに強烈に警告。

### 4.2 クリック時の「ツールチップ詳細ポップアップ」イメージ
ランプをクリック（またはホバー）した際、GKL内の確定グリフ知識（`ItemKnowledge`）から引き出した燃費要因の内訳と、お祈りステータスの現状をクリアに表示します。

```text
┌────────────────────────────────────────┐
│  ⛽ 燃費＆リソース寿命詳細              │
├────────────────────────────────────────┤
│  現在の燃費効率: 🟡 [DRIVE] (やや不良)  │
│                                        │
│  [燃費の要因内訳]                      │
│  • 軽負荷 (Burdened)       : +1.0      │
│  • 装備中の指輪 (1個)       : +1.0      │
│  ───────────────────────────────────  │
│  合計消費ペース           : 2.0 / ターン│
│                                        │
│  [燃料（航続距離）の目安]              │
│  • 餓死(Fainting)まで     : 約 180 歩   │
│  • 手持ちの安全な食料     : 約 300 歩分 │
│  • 神へのお祈り回復       : 🟡 クールダウン中 │
│                             (あと約 450歩) │
└────────────────────────────────────────┘
```

## 5. クライアント組み込み用コード設計案

本機能を疎結合に実装するため、`src/core/knowledge/state/` 付近に新設する `PrayerStatusTracker` のコンポーネントクラスの設計骨子です。

```typescript
/**
 * PrayerStatusTracker.ts
 * 神のご機嫌およびお祈りクールダウンを非侵襲的にエミュレートするクラス
 */
export class PrayerStatusTracker {
  private state: 'SAFE' | 'COOLDOWN' | 'DISPLEASED' = 'SAFE';
  private approximateCooldown: number = 0;

  constructor() {
    // 既存の WebUICore / GKL のメッセージストリーム・シグナルを購読
    // (Stage 5 の MessageContextResolver との連携を想定)
  }

  /**
   * Cコアから送られてきたメッセージシグナルを評価し、ステータスを確定する
   */
  public handleMessageSignal(contextId: string, rawMessage: string): void {
    // お祈り確認プロンプト等からの開始トリガーは上位レイヤーで検知し、ここを叩く
    
    switch (contextId) {
      case 'PRAY_SUCCESS':
        this.state = 'COOLDOWN';
        this.approximateCooldown = 1000; // 雑な安全最大値でロック
        break;

      case 'PRAY_DISPLEASED':
        this.state = 'DISPLEASED';
        this.approximateCooldown = 0;
        break;

      case 'OFFER_RECONCILIATION': // 祭壇での和解ログ
        this.state = 'SAFE';
        this.approximateCooldown = 0;
        break;

      case 'OFFER_HOPEFUL': // 祭壇での希望ログ（怒りは解けたがクールダウン中）
        if (this.state === 'DISPLEASED') {
          this.state = 'COOLDOWN';
          this.approximateCooldown = 500; // 暫定で中間の猶予を与える
        }
        break;
    }
  }

  /**
   * 毎ターンのプレイヤー行動完了時(poskeyイベント等)に呼び出され、カウンターを減算
   */
  public updateTurn(): void {
    if (this.state === 'COOLDOWN' && this.approximateCooldown > 0) {
      this.approximateCooldown--;
      if (this.approximateCooldown === 0) {
        this.state = 'SAFE';
      }
    }
  }

  /**
   * 燃料計の予備タンク計算用にお祈りリソースの価値（満腹度換算）を返す
   */
  public getPrayerNutritionReserve(): number {
    return this.state === 'SAFE' ? 900 : 0;
  }

  /**
   * UI表示用の詳細ステータスオブジェクトをエクスポート
   */
  public getStatusForUI() {
    return {
      state: this.state,
      cooldownEstimated: this.approximateCooldown,
      isAvailable: this.state === 'SAFE'
    };
  }
}
```

## 6. 本アプローチのメリットと今後のタスク

1. **非破壊的移行の担保**:
   C言語ソースの変更やセーブデータの破壊を行うことなく、JavaScript/TypeScript層のロジック追加だけで完結するため、全テスト（1092件）の整合性を100%維持できます。
2. **オオカミ少年化の防止**:
   お祈り可能までの歩数を「約450歩」のように大まかに丸めて提示することで、1ターン単位の細かい乱数ブレに左右されない、頼れるロードインジケーターとして機能します。
3. **Stage 5 の実証ユースケース**:
   現在進行中の「Stage 5: メッセージシグナル化刷新」において、メッセージログを客観事実（シグナル）に昇格させて状態変化の燃料にする、最高のショーケース・実戦コードとなります。
