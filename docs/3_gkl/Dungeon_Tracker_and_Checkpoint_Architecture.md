# ダンジョン探索トラッカー＆チェックポイント（箱・旗立て）仕様・構想書

本書は、NetHack Game Knowledge Layer (GKL) における**ダンジョン探索トラッカー（全階層の探索・施設・オブジェクト履歴の統合表示）**および、ゲーム内行動をプロトコルとした**チェックポイント／拠点マーカー（🚩）**と**箱トラッキング**の設計思想・仕様・UI構想をまとめた公式構想書です。

---

## 1. 背景と課題意識 (Motivation & Problem Statement)

### 1.1 プレイヤーズ・ニーズ
NetHackの探索において、プレイヤーは常に以下のような「後で再訪したい情報」に直面します：
- 鍵や施錠具がなくて一旦スルーした宝箱・チェスト
- 重すぎて持ち歩けない大量の金貨、予備の武具、呪文の書を集積した「拠点（ベースキャンプ）」
- 序盤は危険すぎて近寄れないが、後で刈り取りたい「蜂の巣」や、後で利用したい「泉」「祭壇」
- 「どの階に何を置いてきたか」「どの階にスルーした箱があったか」の記憶負担

### 1.2 従来の技術的障壁
これらを外部UI（WebUI / GKL）側でメモ・ピン留めしようとした場合、以下の深刻な壁が存在していました：

1. **パーマデスとライフサイクルの非同期（ゴミデータ問題）**
   - 冒険手帳（伝承図鑑）のようなメタプログレッション（全冒険共通の永続知識）と異なり、ダンジョンのオブジェクト情報は**「その回の冒険（ラン）が終了（死亡）したら完全に破棄されるべき」**情報である。
   - WebUI側で独自にLocalStorage等へ永続化すると、死亡時やセーブデータ巻き戻し時に前世のピンが亡霊のように残り、情報の陳腐化・不整合を引き起こす。
2. **C言語ソースコード改変の禁止（アーキテクチャ方針）**
   - WASMバイナリやNetHack Cソースコード本体はフォーク・改変せず、バニラ相当の描画・通信プロトコルを維持する方針である。
3. **NetHack画面描画（Glyph）の制約**
   - **重なり箱の不可視性**: 1マスに複数の箱が重なっていても、画面上には一番上の1個のグリフしか描画されない。
   - **Engraving（刻み文字）の中身の不可視性**: ロード復帰直後やフロア移動直後、刻み文字はそのマスに乗って調べるまで「床に刻み文字がある」というグリフ情報しか得られず、テキスト内容（Prefixなど）での判別は不可能。

## 2. コア設計思想 (Core Philosophy)

### ① 関心の完全分離 (Decoupling)
「箱の存在」と「チェックポイント（旗立て）」を同一視せず、完全に分離します。
- **箱トラッキング**: ダンジョン内に存在する箱を客観的に数えて把握する機能（受動的）。
- **旗立て（🚩）**: プレイヤーが明示的に「ここが重要！」とマークする能動的なチェックポイント機能。

### ② 永続化はNetHackセーブデータに完全相乗り
WebUI側で独立した永続化DBを持たず、**NetHack本体のセーブデータが復元するダンジョンマップ情報（グリフ配置）から動的に再構築**します。
これにより：
- 死亡時はNetHackがセーブファイルを消去するため、**ゴミデータ問題が原理的にゼロ（100%解決）**。
- 中断セーブ＆ロード時も、復元されたフロアマップのグリフを走査するだけで正確に情報が蘇る。

### ③ 空間幾何学シグナルプロトコル（プレイヤールール）
C言語ソースを一切改変せず、文字列も読めない制約を突破するため、**「マップ上のグリフの幾何学的配置（並び方）」そのものをシステムへの指示シグナルとするプレイヤールール**を定義します。

### ④ GKL基底レイヤーとしての「空間幾何学エンジン」の責務分離
空間幾何学フィルター（パターン認識）は、特定のUIや機能（DungeonTracker）の従属物ではなく、**GKL（Game Knowledge Layer）の基底認識レイヤー（Perception Layer）**に位置づけます。
これにより、複数の独立した機能がこの基盤エンジンを利用する構造となります：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Consumers / Feature Layer                       │
│ ┌───────────────┐ ┌────────────────┐ ┌────────────────┐ ┌────────────┐ │
│ │ CheckPoint    │ │ DungeonTracker │ │ CustomTile     │ │ Tactical   │ │
│ │ (旗立て・拠点)│ │ (踏破サマリー) │ │ (拡張描画/FX)  │ │ Advisor    │ │
│ └───────┬───────┘ └───────┬────────┘ └───────┬────────┘ └─────┬──────┘ │
└─────────┼─────────────────┼──────────────────┼────────────────┼────────┘
          │                 │                  │                │ 利用
┌─────────▼─────────────────▼──────────────────▼────────────────▼────────┐
│             GKL Core: SpatialPatternEngine (空間幾何学基盤)             │
│  - 2マス隣接Engraving検出 (CheckpointDetector)                         │
│  - 密集コンテナ/重ね箱クラスタ検出 (ContainerClusterDetector)          │
│  - 特殊部屋・地形パターン認識 (RoomFeatureClassifier: 蜂の巣, 金庫等)   │
│  - 重心・中間座標（Sub-pixel Centroid）計算                            │
├────────────────────────────────────────────────────────────────────────┤
│             AreaStateManager (生グリフ・マップ走査・状態管理)          │
└────────────────────────────────────────────────────────────────────────┘
```

## 3. 仕様詳細 (Specifications)

### 3.1 箱トラッキング (Container Tracking)

各フロアでプレイヤーが目視・記憶したマスにあるコンテナ系グリフを集計します。

- **対象オブジェクト**:
  - `LARGE_BOX`, `CHEST`（チェスト、大箱）
  - `SACK`, `OILSKIN_SACK`, `BAG_OF_HOLDING`（各種袋）
- **判定ロジック**:
  - 各フロアの探索済みマスに存在する箱グリフの個数を集計。
  - フロアサマリーには `📦箱x1` や `📦箱x3` のように表示。
- **特徴**:
  - プレイヤーが何もしなくても、フロアを歩いて視界に入れるだけで自動集計される。

#### 3.1.1 開封・未開封（施錠）のメッセージ連動（同一Run内限定トラッキング）
NetHackの仕様上、画面グリフ単体では施錠（Locked）と解錠（Unlocked）は同一タイルであるため、プレイヤーの操作メッセージから状態を学習・キャッシュします：

| プレイヤーの操作 / メッセージ | トラッカー上の箱ステータス |
| :--- | :--- |
| 初めて視界に入った（遠目から見た） | `📦 箱 (状態: 未調査)` |
| 開けようとして `It is locked.` | `🔒 施錠箱 (鍵が必要)` |
| 鍵/ピッキングで `You succeed in picking the lock.` | `📦 開封済み` に更新 |
| 破壊して `You break the lock!` | `📦 開封済み (鍵破壊)` に更新 |

- **ライフサイクル（同一Run限定）**:
  - この施錠/解錠ステータスは**同一Run（ブラウザセッション）内のメモリキャッシュ**として保持されます。
  - **実用価値**: 「プレイ中に後から鍵や施錠具、ノックの杖を拾った際、どの階層に戻れば未開錠の箱があるか」がトラッカーで瞬時に分かり、探索ロス（無駄なターン消費や飢餓リスク）を劇的に防ぐことができます。
  - ※ブラウザのリロード時は「箱がある（📦）」という基本事実のみがグリフから復元され、施錠状態は「未調査」へと安全にフォールバックします。

---

### 3.2 旗立てプロトコル (Checkpoint Flag: 🚩)

プレイヤーが任意のフロア・任意の場所にチェックポイントや拠点を宣言するための仕組み。

#### 【プレイヤールール】
> **「床の刻み文字（Engraving）を、隣接する2マス（水平・垂直・斜めの8近傍）に連続して刻む」**

```text
【配置例】
[ . ][ ✍️ ][ ✍️ ][ . ]   ← 水平に2マス並べる
         または
[ ✍️ ]
[ ✍️ ]                   ← 垂直に2マス並べる
```

#### なぜこのルールなのか？（設計の必然性）
1. **完全ノーコスト・2ターンで可能**:
   - ダガーなどの道具すら不要。床のホコリに指（`#engrave` -> `-`）で適当な文字（`x` 等）を2回刻むだけで成立。
2. **自然生成との重複・誤認率ゼロ**:
   - NetHackのダンジョン自動生成において、刻み文字が2マス連続で隣接生成されるアルゴリズムは存在しない。100%プレイヤーの意図と断定可能。
3. **ロード復帰直後でも100%判定可能**:
   - 文字列（テキスト）を読まず、グリフマップ上の `ENGRAVING` タイルが隣接しているかどうかの幾何計算（チェビシェフ距離=1）だけで一瞬で検出できる。
4. **どこでも・何にでも使える**:
   - 箱の横に刻めば「拠点（ベースキャンプ）」。
   - スルーした鍵箱の横に刻めば「未開封の箱マーカー」。
   - 蜂の巣や泉、テレポート罠の横に刻めば「後で再訪する特殊スポット」。
5. **フロアあたり最大1個の原則**:
   - 1フロアに隣接ペアが複数あっても、サマリー上はフロアごとに1つの `🚩` として表現（UIの視認性を保つため）。

### 3.3 ダンジョン探索トラッカー（履歴統合サマリー）

現在NetHack-wasm-webUIには存在しない、**「これまで踏破した全フロアの状況を一望できる統合トラッカー」**を新設します。

#### データモデル（階層ノード）
各フロア（ダンジョン番号 `dnum` × 階層番号 `dlevel`）ごとに以下の情報を保持：
```typescript
interface FloorSummary {
  dnum: number;            // ダンジョン分岐ID (0: メイン, 1: 鉱山, 2: 倉庫番 等)
  dlevel: number;          // 階層の深さ (1〜)
  branchName: string;      // 分岐名 (Dungeon of Doom, Gnomish Mines 等)
  visited: boolean;        // 訪問済みフラグ
  hasFlag: boolean;        // 🚩 プレイヤーの旗（隣接Engraving）が存在するか
  flagCoord?: { x: number, y: number }; // 旗の座標
  containersCount: number; // 視認されている箱・袋の数
  features: {
    hasStairsUp: boolean;   // <
    hasStairsDown: boolean; // >
    altar?: { align: string }; // 祭壇 (Neutral, Lawful, Chaotic)
    shop?: { type: string };   // 店 (General, Food, Armor 等)
    sinkCount: number;         // シンク
    fountainCount: number;     // 泉
    throne: boolean;           // 玉座
  };
}
```

### 3.4 ロード再開時の課題と `#overview` コマンド連携 (Overcoming the Load-Resume Gap)

#### 【課題：ロード直後の過去フロア情報の欠落】
WebUI側のメモリは「現在表示されているフロア」のグリフ情報しか受け取れません。そのため、ブラウザのリロードやセーブデータからの再開直後は、**「過去に訪れたフロア（D:1〜D:N）の情報が手元にないため、再開したフロアからの記録になってしまう」**という問題が生じます。

#### 【解決策：NetHack標準の `#overview` (`Ctrl+O`) コマンド連携】
実は、NetHack本体（3.6 / 5.0系）には、まさにこの**「訪問した場所リスト」をセーブデータ内部（`mapseen` 構造体）で完璧に記録・永続化している機能**が標準装備されています。

- **`#overview` コマンド（または `Ctrl+O`）**:
  - ゲーム中いつでも呼び出し可能な標準拡張コマンド。
  - ゲームオーバー時に開示される「ダンジョン踏破履歴」と同一の内部データ（`dungeon.c: show_overview()`）。
  - **出力内容**: 訪れたことのある全フロアの深さ、ダンジョン分岐名（メイン、鉱山、倉庫番等）、階段（上り・下り）、祭壇（属性・神名）、店（店舗種別）、泉、シンク、玉座など。

#### 【ハイブリッド復元アーキテクチャ】
1. **ベース情報の復元 (`#overview` パース)**:
   - トラッカーモーダルを開いた際、またはセーブロード復帰時に、WebUIから自動的に `#overview` を実行（またはテキストメニュー出力をキャプチャ）。
   - これにより、**ロード直後でも過去の全踏破フロアと施設一覧が一瞬で100%復元**される。
2. **詳細オーバーレイ（箱 ＆ 🚩）**:
   - プレイヤーが実際にそのフロアに滞在している間に、マップグリフから「箱の個数（📦）」および「隣接刻み文字による旗（🚩）」をリアルタイムにマージ。
   - 箱や旗がないフロアでも、`#overview` 由来の階段・施設情報は常に完璧に表示される。

### 3.5 空間幾何学シグナルプロトコルの応用：特殊地形検出とフロアメッセージ (Contextual Floor Messages)

「グリフの空間配置・隣接関係をシグナルとして読む」プロトコルは、単なる旗立て（🚩）にとどまらず、**「特殊地形の自動検知」**や**「フロア進入時のスマート・コンテキストメッセージ通知」**へと大きく発展させることができます。

#### ① 「🚩」＋「隣接オブジェクト」による自動コンテキスト分類
プレイヤーが立てた旗（隣接刻み文字）のすぐ隣（周囲1マス）に何があるかを見るだけで、旗の意味（タグ）を自動判別できます：
- **`🚩` ＋ 箱（📦）** ➔ `[拠点・デポ]`（荷物置き場）
- **`🚩` ＋ 泉（⛲）** ➔ `[水場・聖水候補]`（後でディップ・飲用に戻る場所）
- **`🚩` ＋ 祭壇（⛪）** ➔ `[信仰・生贄ベース]`
- **`🚩` ＋ 施錠扉（🚪）** ➔ `[未開錠の小部屋]`
- **`🚩` ＋ 特殊罠（^）** ➔ `[緊急脱出テレポート / レベルテレポート]`

#### ② 自然地形の幾何学パターン自動検出（無意識シグナル）
プレイヤーが刻み文字を刻まなくても、ダンジョン生成の幾何学的なタイル配置から「特殊な部屋」を自動認識します：
- **蜂の巣（Beehive）の検知**:
  - 蝋（Wax）の床、または密集した蜂（`f`）の部屋 ➔ **「⚠️ 蜂の巣を検知（ロイヤルゼリーの宝庫 / 毒針注意）」**
- **隠し金庫（Vault）の検知**:
  - 外周が壁で完全に囲まれた孤立した2x2〜3x3の部屋の中にゴールド（`$`）が存在 ➔ **「💰 隠し金庫（Vault）の兆候を検知（ツルハシまたはテレポートが必要）」**
- **兵舎（Barracks）の検知**:
  - ベッド（Bed）などの家具が整列している部屋 ➔ **「⚔️ 兵舎を発見（多数の兵士と武具ドロップ）」**

#### ③ フロア到着時のスマート・トースト通知（TacticalAdvisor連携）
階段を昇降してフロアに入った瞬間、GKLの `TacticalAdvisor` / 通知システムと連動して、プレイヤーの記憶を呼び覚ますトースト通知を表示します：

```text
┌─────────────────────────────────────────────────────────────┐
│ 🚩 D:7 (ベースキャンプ) に到着しました                       │
│    保管箱 4個 / 中立祭壇 があります                         │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ 💡 リマインダー (D:3)                                        │
│    この階層には以前マークした [🔒 未開錠の箱] が残っています │
│    （現在、所持品に「スケルトンキー」を所持しています）     │
└─────────────────────────────────────────────────────────────┘
```

## 4. UI / UX 構想 (UI Concept & Mockup)

### 4.1 専用モーダル・アーキテクチャの踏襲 (Dedicated Modal Pattern)
本トラッカーは、既存の **`GenocideModal` (虐殺アシスタント)**、**`WishModal` (願い)**、**`PolymorphModal` (変化)** と全く同じ**「能動的アクションに応答する専用モーダル体系」**として実装します。

- **シグナルとトリガー**:
  - プレイヤーの明示的な操作（ヘッダーの `🗺️ 探索記録` ボタン、または `Ctrl+M` / `Ctrl+O`）を検知。
  - あるいはNetHack標準の `#overview` コマンド実行シグナルをフック。
- **GKLモーダル標準コンポーネント**:
  - `ModalManager.js` の管理下に `DungeonTrackerModal` を追加。
  - テキスト主体のNetHack出力を、ブランチ別タブ、施設アイコンバッジ、リッチテーブルへとグラフィカルに昇華。

### 4.2 ダンジョン探索トラッカー・モーダル (`DungeonTrackerModal`)

ショートカットキー（例: `Ctrl+M` やヘッダーボタン `🗺️ 探索記録`）で開く専用モーダル画面。

```text
┌──────────────────────────────────────────────────────────────┐
│ 🗺️ ダンジョン探索トラッカー (Dungeon Exploration Tracker)    [×] │
├──────────────────────────────────────────────────────────────┤
│ [運命の迷宮]  [ノームの鉱山]  [倉庫番]  [全ブランチ一覧]        │
├──────────────────────────────────────────────────────────────┤
│  階層   │ 🚩 │ 主な施設 / チェックポイント        │ 箱/デポ  │
├─────────┼───┼────────────────────────────────────┼──────────┤
│  D: 1   │   │ < >                                │          │
│  D: 2   │   │ < > ⛲(泉)                         │          │
│  D: 3   │ 🚩│ < > 🔒(施錠箱あり・未開封)          │ 📦 x1    │
│  D: 4   │   │ < > 🏪(一般商店)                   │          │
│  D: 5   │   │ < > 🚰(シンク)                     │          │
│  D: 6   │   │ < >                                │          │
│  D: 7   │ 🚩│ < > ⛪(中立祭壇) [★拠点ベースキャンプ] │ 📦 x4    │
│  D: 8   │   │ < > 🐝(蜂の巣)                     │          │
│  D: 9   │   │ <   (現在地)                       │          │
└─────────┴───┴────────────────────────────────────┴──────────┘
 ※ 🚩の立て方: 任意の場所で `#engrave` を使い、隣り合う2マスに文字を刻むと自動登録されます。
```

### 4.3 画面上・ミニマップとの連動
- **ミニマップ上の表示**:
  - `🚩` がある座標には、ミニマップ上で赤旗アイコンまたはパルスアニメーションを表示。
  - 箱が存在するマスには小さな `📦` アイコンを重畳表示。
- **フロア到着時のトースト通知**:
  - 旗が立っているフロアに戻ってきた時：
    > `🚩 チェックポイントのある階層に到着しました (D:7)`

### 4.4 ビジュアル演出連携：中間座標とパーティクルFX (Visual FX Integration)
GKLの演出トリガー設計思想（`docs/3_gkl/GKL_Visual_FX_Event_Architecture.md`）に基づき、**「GKLは幾何学的な事実と座標情報を提供するだけに徹し、レンダラー（UI側）が自由に彩る」**アーキテクチャを展開できます。

#### ① 中間座標（重心・Midpoint）の提供
隣接する2つの刻み文字（Engraving）が検出された際、GKLは単なる1マスの座標ではなく、2マスの境界・中心となる**中間座標（サブピクセル/浮動小数点座標）**をクライアントへ提供します：

```typescript
// GKLが提供するチェックポイント情報
interface CheckpointGeometry {
  cellA: { x: number, y: number };
  cellB: { x: number, y: number };
  center: { x: number, y: number }; // (xA + xB) / 2, (yA + yB) / 2
  orientation: 'horizontal' | 'vertical' | 'diagonal';
}
```

#### ② クライアント（レンダラー側）での演出表現
クライアント側（DOM、Canvas、WebGL/PixiJSなど）は、この `center` 座標を受け取り、ゲームプレイを阻害しないアンビエント（環境）演出を重ねて描画できます：

- **焚き火・野営の煙パーティクル**:
  - ベースキャンプ感あふれる小さな火の粉や煙が立ち上る演出。
- **神秘的な光の柱 / 結界オーラ**:
  - マジックポイントやチェックポイントを想起させる、淡い青や金の光の粒子。
- **たなびく小さな旗（🚩）のオーバーレイ**:
  - 2マスの境目にスッとピンが立ち、風に揺れるアニメーション。

#### ③ 入力テンポを損なわない非干渉設計
NetHack本来の「サクサク進むキー入力」を一切邪魔しないよう、これらの演出はアニメーションタイマーによる入力待ち（ブロッキング）を行わず、純粋な視覚的オーバーレイレイヤーとして動作します。

## 5. ボトムアップ構築ロードマップ (Implementation Roadmap)

基底エンジン（`SpatialPatternEngine`）を分離したことにより、手戻りのない堅牢なボトムアップ開発が可能になります。

```text
┌─────────────────────────────────────────────────────────────────┐
│ Step 1: SpatialPatternEngine の TDD 単体テスト開発              │

└────────────────────────────────┬────────────────────────────────┘
                                 ▼

│ Step 2: GKL AreaStateManager との結合                           │

└────────────────────────────────┬────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ Step 3: ダンジョン履歴マネージャ ＆ #overview コマンド連携      │
│ ➔ ロード復帰時の過去フロア復元 ＆ 同一Run内の施錠ステート保持   │
└────────────────────────────────┬────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
```

- **Step 1: 基盤エンジンの確立**:
  - `SpatialPatternEngine.js` と `SpatialPatternEngine.test.js` を作成。
  - テキスト・UI・NetHack起動不要で、隣接Engraving（🚩）や箱密集度の幾何計算を100%テスト検証。

- **Step 3: 履歴スナップショットと `#overview` 連携**:
  - 階層移動時のスナップショット記録、および `#overview` テキストメニューのパースロジック。
  - `It is locked.` 等のメッセージをトリガーにした施錠キャッシュ。

  - 既存の `GenocideModal` / `WishModal` パターンを踏襲したリッチな一覧UIの実装。
- **Step 5: ビジュアル・アンビエント演出**:
  - `center` 座標を活用したミニマップピン留めや、焚き火パーティクル演出の接続。

## 6. まとめ

本アーキテクチャの最大の強みは、**「ゲームのCソースコード改変ゼロ」「NetHackのセーブデータに完全相乗り」「誤認率ゼロの幾何学プロトコル」**をすべて両立させている点にあります。

プレイヤーにとっては「指で床にチョークマークを2つ残す」という自然な冒険者ロールプレイを行うだけで、WebUI側がハイテクなダンジョン探索ナビゲーションとして応えてくれる、極めて完成度の高いシステム構想です。
