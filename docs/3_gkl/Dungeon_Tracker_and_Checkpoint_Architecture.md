# ダンジョン探索トラッカー＆フロアメモ仕様・アーキテクチャ設計書

> [!IMPORTANT]
> **C コア標準機能 (`mapseen` / `#annotate`) への全面移行とアーキテクチャ純化 (2026-10-20)**
> これまで検討されていた「床の2マスEngravingによる幾何学旗立て（🚩）」および「JS側での独自フロア履歴キャッシュ制御」を抜本的に見直し、**NetHack C コアが標準で保持・永続化している `mapseen`（`#overview` のバックボーン）と `#annotate` コマンドを中核真値（SSOT）とする設計へと全面刷新**しました。
> - **セーブデータ完全相乗り**: メモや踏破履歴はNetHackのセーブファイルに直接記録されるため、パーマデス（死亡時のデータ消去）やセーブ＆ロードと100%連動し、ゴミデータや亡霊マーカー問題が原理的にゼロになります。
> - **推論・キャッシュコードの全廃**: JS側でフロアごとの施設や過去マップを記憶・スキャンする複雑な制御コードを完全に撤廃し、C コアの `svm.mapseenchn` を Direct Binding で直引きするシンプルなパイプラインに純化します。
> - **操作性の向上**: プレイヤーはゲーム内ターンを消費して床に文字を刻む必要がなく、UI上のメモダイアログから快適に注釈を付与できます。

本書は、NetHack Game Knowledge Layer (GKL) における**ダンジョン探索トラッカー（全階層の踏破・施設・メモ一覧）**および、ガイダンス・アドバイザー基盤の公式アーキテクチャ仕様書です。

---

## 1. 背景と設計思想 (Motivation & Architecture Philosophy)

### 1.1 従来の技術的障壁と過剰設計の反省
NetHack のプレイにおいて、「どの階層に何を置いてきたか」「どの階層に未探索の店や祭壇があったか」を把握する探索トラッカーは必須の機能です。
しかし、これを外部（WebUI / GKL）側で実現しようとした際、以下の課題がありました：

1. **パーマデスとライフサイクルの非同期（亡霊マーカー問題）**:
   - WebUI側で独自に `localStorage` や IndexedDB にフロア情報を永続化すると、死亡時やセーブデータ巻き戻し時に前世のピンが亡霊のように残ってしまう。
2. **地形の動的変化とハッシュの脆さ**:
   - フロアの識別に地形データハッシュを使おうとすると、壁の掘削・モンスターによる壁破壊・ドアの破壊によってハッシュが変わり、マーカーが二度と復元できなくなる。
3. **ゲーム内 Engrave（刻み文字）方式の煩雑さ**:
   - 埃への指刻みは数歩歩いただけで風化して消え、石に刻むにはダイヤモンドやダガーが必要。何よりメモを残すためにゲーム内ターンを消費してしまう。

### 1.2 解決の鍵：C コア標準機能 (`mapseen` / `#overview` / `#annotate`)
NetHack 3.6 / 5.0 には、まさにこの課題を完璧に解決する仕組みが標準で組み込まれています。
- **`#annotate` コマンド**: プレイヤーが各フロアに任意のテキストメモ（注釈）を付与する公式機能。
- **`mapseen` 構造体 (`svm.mapseenchn`)**: プレイヤーが訪れて視界に入れた全フロアの「階段、祭壇（属性）、店（種別）、泉、シンク、玉座、特殊フロアフラグ、および上記 `#annotate` のメモ」をセーブデータ内部で自動追跡・永続化しているリンクリスト。
- **`#overview` コマンド (`Ctrl+O`)**: `mapseen` の情報を一覧表示する公式メニュー。

この **NetHack 本体が数十年にわたり磨き上げてきた公式の踏破追跡機構を Direct Binding で直引きする** ことで、JS 側の独自キャッシュを全廃し、最高精度のトラッカーを最小のコード量で実現します。

## 3. C コア内部データ仕様 (`struct mapseen`)

NetHack 5.0 (`include/dungeon.h`) における `mapseen` の完全なデータ構造です。

```c
typedef struct mapseen {
    struct mapseen *next; /* 次のフロアノードへのポインタ */
    branch *br;           /* 所属ダンジョンブランチ */
    d_level lev;          /* 階層識別 (dnum, dlevel) */
    
    /* ① 観測済み地形・施設情報 */
    struct mapseen_feat {
        Bitfield(nfount, 2);   /* 泉の数 */
        Bitfield(nsink, 2);    /* シンクの数 */
        Bitfield(naltar, 2);   /* 祭壇の数 */
        Bitfield(nthrone, 2);  /* 玉座の数 */
        Bitfield(ngrave, 2);   /* 墓の数 */
        Bitfield(ntree, 2);    /* 木の数 */
        Bitfield(water, 2);    /* 水路の有無 */
        Bitfield(lava, 2);     /* 溶岩の有無 */
        Bitfield(ice, 2);      /* 氷の有無 */
        Bitfield(nshop, 2);    /* 店の数 */
        Bitfield(ntemple, 2);  /* 寺院 (神官) の数 */
        Bitfield(msalign, 2);  /* 祭壇の属性 (0:なし, 1:Lawful, 2:Neutral, 3:Chaotic) */
        Bitfield(shoptype, 5); /* 店舗種別 (一般, 食料, 武器, 防具, 巻物, 杖 等) */
    } feat;

    /* ② 特殊フロア・進行フラグ */
    struct mapseen_flags {
        Bitfield(notreachable, 1);     /* 戻れない階層か */
        Bitfield(forgot, 1);           /* 忘却状態 */
        Bitfield(knownbones, 1);       /* 既知のボーンフロア */
        Bitfield(oracle, 1);           /* デルポイの神託所 */
        Bitfield(sokosolved, 1);       /* 倉庫番クリア済み */
        Bitfield(bigroom, 1);          /* 大部屋 */
        Bitfield(castle, 1);           /* 城 */
        Bitfield(castletune, 1);       /* 跳ね橋のメロディヒント */
        Bitfield(valley, 1);           /* 嘆きの谷 */
        Bitfield(msanctum, 1);         /* 聖域 */
        Bitfield(vibrating_square, 1); /* 震える四角形 (発見済みか) */
    } flags;

    /* ③ プレイヤーのフロアメモ */
    char *custom;         /* #annotate で入力された注釈テキスト (未設定時は NULL) */
    unsigned custom_lth;  /* 文字列長 */
} mapseen;
```

## 4. Direct Binding プロトコル (`shim_bridge.c`)

### 4.1 コマンド定義
`shim_bridge.c` に以下のコマンドを追加します：

```c
enum ShimBridgeCmd {
    /* 既存のコマンド ... */
    SHIM_CMD_DUMP_MAPSEEN = 0x34, /* buf=MapseenNodeEntry[], len=max -> 全踏破階層のダンプ */
};
```

### 4.2 ダンプ用固定長構造体 (`MapseenDumpEntry`)
JavaScript と C の間で高速にゼロコピー/一括転送するためのメモリレイアウト：

```c
typedef struct {
    int32_t dnum;              /* ダンジョン番号 (0: Main, 1: Mines, 2: Sokoban 等) */
    int32_t dlevel;            /* 階層の深さ (1〜) */
    
    /* feat ビットパック */
    uint16_t nfount;
    uint16_t nsink;
    uint16_t naltar;
    uint16_t msalign;          /* 0: None, 1: Lawful, 2: Neutral, 3: Chaotic */
    uint16_t nshop;
    uint16_t shoptype;         /* 店舗種別 ID */
    uint16_t nthrone;
    uint16_t ntemple;
    
    /* flags ビットパック */
    uint32_t flags;            /* sokosolved, castle, oracle, vibrating_square 等 */
    
    /* custom 注釈文字列 */
    char custom[64];           /* #annotate テキスト (UTF-8 / ASCII) */
} MapseenDumpEntry;
```

### 4.3 C 実装ロジック (`shim_bridge.c`)
```c
case SHIM_CMD_DUMP_MAPSEEN: {
    MapseenDumpEntry *dst = (MapseenDumpEntry *) buf;
    int max_entries = len / sizeof(MapseenDumpEntry);
    int count = 0;
    struct mapseen *curr = svm.mapseenchn;

    while (curr && count < max_entries) {
        dst[count].dnum = curr->lev.dnum;
        dst[count].dlevel = curr->lev.dlevel;
        dst[count].nfount = curr->feat.nfount;
        dst[count].nsink = curr->feat.nsink;
        dst[count].naltar = curr->feat.naltar;
        dst[count].msalign = curr->feat.msalign;
        dst[count].nshop = curr->feat.nshop;
        dst[count].shoptype = curr->feat.shoptype;
        dst[count].nthrone = curr->feat.nthrone;
        dst[count].ntemple = curr->feat.ntemple;
        
        dst[count].flags = (curr->flags.sokosolved ? 0x01 : 0)
                         | (curr->flags.castle ? 0x02 : 0)
                         | (curr->flags.oracle ? 0x04 : 0)
                         | (curr->flags.vibrating_square ? 0x08 : 0)
                         | (curr->flags.bigroom ? 0x10 : 0);

        if (curr->custom && curr->custom[0]) {
            strncpy(dst[count].custom, curr->custom, sizeof(dst[count].custom) - 1);
            dst[count].custom[sizeof(dst[count].custom) - 1] = '\0';
        } else {
            dst[count].custom[0] = '\0';
        }

        count++;
        curr = curr->next;
    }
    return count; /* 取得件数を返す */
}
```

## 5. UI / UX 仕様 (Client Features)

### 5.1 UI配置方針とセッションスコープ設計
ダンジョン踏破記録（`mapseen`）および階層メモ（`#annotate`）は、セッション横断の永続コレクション（冒険手帳 `CodexModal`）とは異なり、**「現在の1プレイ（セッション）限定の進行状態」** です。
また、メインヘッダーのボタン過多を防ぐため、新規独立ボタンをヘッダーに配置せず、**既存のHUD・ダイアログの「現在地表示」をインタラクティブなトリガーとして活用** します。

- **呼出トリガー**:
  1. **HUD ステータスバーの階層表示**（例: `地下1階 (Dlvl:1)`）をクリック。
  2. **`👤 ステータス` ダイアログ (`CharacterStatusModal`)** 内の「現在地」項目をクリック。
  3. ショートカットキー（`Ctrl+O` または `Alt+A`）。
- **呼出先モーダル**:
  - 軽量なセッション専用ダイアログ **`FloorTrackerModal`（フロア記録・階層メモ）** を起動。
  - 現在階層の観測施設、全踏破ブランチ一覧、および `#annotate` メモ入力欄を表示。

---

### 5.2 「現在地ピン打ち」＆ クイックタグ入力方式 (ASCIIセーフ設計)
NetHack C コアの入力処理（`getlin`）はマルチバイト文字（日本語 UTF-8 等）を想定しておらず、直接日本語を流し込むとバッファ溢れや文字化けの原因となります。
そのため、本システムでは **「C コア側には純粋な ASCII マーカーコードのみを保存し、表示時に JS 側で日本語/英語ラベルに展開する」** アーキテクチャを採用します。

また、複雑な座標選択やドラッグ＆ドロップなどの余計なUIを排除し、**「プレイヤーが今立っている現在位置 `(u.ux, u.uy)` にピンを打つ」** 方式を採用します。
NetHack のプレイスタイルとして「拠点にしたい部屋」や「未開錠の箱の前」「階段付近」に立った状態で記録するのが最も自然で、誤操作も防止できます。

```text
┌─────────────────────────────────────────────────────────┐
│ 🗺️ 地下3階 (Dlvl:3) のフロアマーカー                     [×] │
├─────────────────────────────────────────────────────────┤
│ 🏛️ 観測施設: 🏪店(一般)  ⛲泉×1                          │
│ 📍 プレイヤー現在地: (x: 42, y: 12)                     │
├─────────────────────────────────────────────────────────┤
│ ［現在地にマーカーを追加］:                              │
│  [🚩 拠点]  [🔒 未開錠の箱]  [🎒 荷物置場]  [⚠️ 危険マス]  │
│                                                         │
│ 登録済みマーカー:                                       │
│  • 🚩 メイン拠点・デポ (x: 42, y: 12)            [削除] │
│  • 🔒 未開錠の箱 (x: 18, y: 8)                  [削除] │
│                                                         │
│ Cコア保存データ: !M:154C,2248                           │
│                                           [ 保存 (Enter) ]│
└─────────────────────────────────────────────────────────┘
```

1. **クイックタグのワンタップ**:
   - `[🚩 拠点]` を押すと、現在地 `(u.ux, u.uy)` と種別IDからマーカーコード（例: `154C`）が生成されリストに追加。
2. **保存とCコア連携**:
   - 「保存」または Enter で、WebUI から C コアへ `#annotate` コマンドを発行（例: `#annotate\r!M:154C,2248\r`）。
   - **IRC (Interactive Request Controller) による安全な書き込み**:
     - Direct Binding は「読み取り専用 SSOT パイプライン」に徹し、書き込みは WebUICore の IRC を通じて実行。
     - 表示抑止（サイレント実行による画面のチラつき防止）およびプレイヤー入力との排他制御を効かせた状態でキーシーケンスを安全に送信。
   - C コア内部の `svm.mapseenchn->custom` に直接 ASCII 文字列として書き込まれ、**公式のセーブデータに安全・自動永続化** される。
   - 書き込み完了後は `SHIM_CMD_DUMP_MAPSEEN (0x34)` で即座に再取得（オンデマンド同期）して UI / ミニマップを更新。

### 5.3 マーカーコード仕様（ASCII エンコーディング ＆ JS辞書展開）
NetHack 公式の `#annotate` 文字列（最大長約64文字）に相乗りし、ミニマップやメインビューポートへピンを表示するための圧縮仕様です。
NetHack のダンジョン最大座標は `x: 0〜79` (7bit: 0〜127)、`y: 0〜23` (5bit: 0〜31) です。

| ビット幅 | 項目 | 内容 |
|---|---|---|
| **4 bit** (0〜15) | マーカー種別 (Type) | 辞書定義（0: 拠点, 1: 箱, 2: 保管品, 3: 危険, 4: 祭壇, 5: 店舗 等） |
| **7 bit** (0〜127) | X 座標 (`u.ux`) | `0 〜 79` |
| **5 bit** (0〜31) | Y 座標 (`u.uy`) | `0 〜 21` |

- **合計ビット数**: **16 bit (2 bytes)**
- **文字列表現（100% ASCII 安全性）**:
  - 接頭辞 `!M:` ＋ 16進数 4 桁（HEX）コードをカンマ区切りで連結。
  - 例: `X=42 (0x2A)`, `Y=12 (0x0C)`, `Type=1 (未開錠の箱)` の場合
    - `(Type << 12) | (X << 5) | Y` = `(1 << 12) | (42 << 5) | 12` = `0x154C`
    - Cコア保存文字列: `!M:154C`（複数時は `!M:154C,2088`）
- **JS辞書引きによる多言語UI展開**:
  C コアには一切マルチバイト文字を通さず、JS 側の辞書テーブルで日英テキストやアイコンを即時展開します。
  - `Type 0`: 🚩 メイン拠点・デポ (Main Base / Depot)
  - `Type 1`: 🔒 未開錠の箱 (Locked Chest)
  - `Type 2`: 🎒 荷物・保管品 (Stashed Items)
  - `Type 3`: ⚠️ 要注意・危険マス (Hazard / Dangerous)
  - `Type 4`: ⛪ 祭壇 (Altar)
  - `Type 5`: 🏪 店舗 (Shop)
- **ミニマップ / HUD 連携**:
  - GKL 側でフロアメモ取得時に正規表現（`!M:([0-9A-Fa-f]{4}(?:,[0-9A-Fa-f]{4})*)`）でピンコードをデコード。
  - ミニマップやマップオーバーレイの該当マス `(42, 12)` に 🔒 アイコンを自動レンダリング。

#### 5.3.1 エリア分割（3×3 / 5×5）による超圧縮と複数ピン拡張
ピン位置を「ピンポイントの1マス」ではなく「大まかなエリア／部屋単位」とする場合、ビット数をさらに削減できます。

| 方式 | X 分割 (bit) | Y 分割 (bit) | 座標 bit | 種別 (4bit) 込 | 表現長 (HEX) | Cコア保存例 |
|---|---|---|---|---|---|---|
| **完全1マス指定 (1×1)** | 80通り (7 bit) | 24通り (5 bit) | 12 bit | **16 bit** | HEX: 4文字 | `!M:154C` |
| **3×3 エリア指定** | 27分割 (5 bit) | 8分割 (3 bit) | 8 bit | **12 bit** | HEX: 3文字 | `!M:18B` |
| **5×5 エリア指定** | 16分割 (4 bit) | 5分割 (3 bit) | 7 bit | **11 bit** | HEX: 3文字 | `!M:17A` |

- **超圧縮によるメリット**:
  1. **複数ピンの埋め込み**:
     - `#annotate` の 64 文字制限下でも、1ピンわずか 3〜4 文字（カンマ含め 4〜5 文字）で済むため、同一フロアに 5〜10 個のマーカーを余裕を持って共存可能。
  2. **NetHack の部屋構造との親和性**:
     - NetHack の通常ダンジョンは 3×3（計9部屋）のグリッドで構成されるため、3×3 エリア指定は「部屋の場所」と直感的に一致し、ミニマップ上でも該当エリアを薄くハイライト描画するのに適している。

#### 5.3.2 ユーザーカスタムスロット ＆ 二重ストレージ分離設計 (localStorage連携)
ユーザーが自由に日本語ラベルやアイコンを設定できるようにするため、**「マーカー配置情報（Run固有）」と「カスタムタグ辞書（ユーザー永続）」を明確に二重分離** します。

```text
┌────────────────────────────────────────────────────────────────────────┐
│ ① プレイ固有データ (Run-Scoped / Cコア SSOT)                           │
│   ・保存先: C コア svm.mapseenchn->custom (NetHack公式セーブデータ)    │
│   ・内容: !M:854C,9248 等 (ID + 座標の純粋な ASCII 列)                 │
│   ・ライフサイクル: キャラクター死亡時にパーマデス連動でリセット       │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ マーカーID (例: 8, 9) で照合
┌──────────────────────────────────▼─────────────────────────────────────┐
│ ② ユーザー設定・カスタム辞書 (Persistent / localStorage)                │
│   ・保存先: ブラウザの localStorage (nethack_custom_marker_slots)      │
│   ・内容: IDごとの表示ラベル・アイコン定義 (ユーザーが自由編集可能)   │
│       - ID 8: { icon: "⚡", label: "耐性死体・食料庫" }                │
│       - ID 9: { icon: "💍", label: "変化の指輪保管場所" }              │
│   ・ライフサイクル: セッション横断で永続 (次回のRunや新キャラでも再利用)│
└────────────────────────────────────────────────────────────────────────┘
```

- **スロット割り当て**:
  - `ID 0 〜 7` (8枠): システム共通固定プリセット（🚩拠点, 🔒箱, 🎒荷物, ⚠️危険マス, ⛪祭壇, 🏪店, 🚪隠し扉, 🕳️落とし穴）
  - `ID 8 〜 15` (8枠): **ユーザーカスタムスロット**（`localStorage` に定義を永続化）
- **メリット**:
  1. **完全な言語・文字数制約の隠蔽（全言語圏対応）**:
     - 日本語等のマルチバイト文字だけでなく、英語であっても公式の 64 バイト制限を超える長文メモ（例: `"Stashed 2 blessed scrolls of charging and unicorn horn in chest"` = 64文字超過）を問題なく登録・表示可能。Cコアへは 1 マーカーあたりわずか 3〜4 バイトの ASCII（`854C` 等）しか送出されない。
  2. **定型文テンプレート（マクロ）としての利便性**:
     - 毎回の冒険で頻出するメモ（例: `"Bones level with high danger"`, `"Main base with neutral altar"`）を定型文スロットとして登録しておくことで、文字入力の手間を全廃し、ワンタップで現在地にテンプレートマーカーを付与できる。
  3. **Run を超えたタグの再利用**:
     - プレイヤーのお気に入りマーカー辞書は `localStorage` に保持されるため、新しい冒険を始めるたびにタグを作り直す手間が一切ない。

## 6. コード純化とリファクタリング計画 (Code Cleanup)

本アーキテクチャの導入により、これまで JS 側で抱え込んでいた複雑なキャッシュコードを大幅に削減します。

| 領域 | 従来の課題（削除対象） | 新アーキテクチャ（純化後） |
| :--- | :--- | :--- |
| **フロア履歴管理** | フロア移動時に JS 側で `landmarkRegistry` やキャッシュマップを退避・復元するコード | **全廃**。全フロア履歴は C コアの `svm.mapseenchn` から常に一括取得。 |
| **施設推論** | グリフ番号やメッセージから「中立祭壇か」「食品店か」を推測・記録するコード | **全廃**。C コア自身が記録した `msalign`, `shoptype` をそのまま表示。 |
| **永続化制御** | ブラウザの `localStorage` 等にフロア情報を保存し、死亡時に消去する同期ロジック | **全廃**。NetHack セーブデータに完全相乗り。 |
| **空間認識エンジン** | 2マス Engrave の幾何計算・重心算出・風化対策 | **全廃**。公式の `#annotate` メモ機構に一本化。 |

## 7. まとめ

NetHack C コアが半世紀近くの歴史の中で洗練させてきた **`mapseen`（`#overview`）と `#annotate`** を真値として Direct Binding で直結することにより：
1. **バグや不整合が原理的に発生しない（SSOT原則の徹底）**
2. **パーマデス・セーブ＆ロードに完全自動対応**
3. **JS 側のコード量を劇的に削減し、メンテナンス性を最大化**

という、プロジェクトにとって最も美しいアーキテクチャが実現します。
